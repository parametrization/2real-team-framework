# Generic Skill: Ontology Rebuild (Semantic-Overlay Resolver)

## Purpose

Reconcile the **hand-curated semantic overlay** of the ontology for files that
changed since the last resolution pass. It reads dirty entries from a checksums
file, derives knowledge **from the code**, updates the overlay + auto-updatable
docs, and marks the entries resolved.

**Scope is the semantic overlay ONLY.** The generated structural index is out of
scope — it is regenerated by its generator, never hand-resolved here.

The optional `scope` argument limits the run: `code`, `docs`, or a specific repo
name; if omitted, process all dirty files.

## Context — curate-semantic + generate-structural model

| Layer | Contents | Update path |
|---|---|---|
| **Semantic overlay** | domain/services/conventions + per-repo internals + hand-edited docs | **this skill** (reads checksums dirty entries, reconciles against code) |
| **Structural index** | generated file/module/symbol graph | the generator (wholesale regen, never hand-edited) |

Roles operating on the overlay:
- **Change Tracker** (hook) — auto-updates the checksums file on every edit to a
  hand-curated file (sets `last_tracked`). It **skips** the structural dir.
- **Change Resolver** (this skill) — reads dirty entries, reconciles, sets
  `last_resolved = last_tracked`.
- **Librarian** (read-only) — surfaces both layers.

A file is "dirty" when `last_tracked != last_resolved`.

### Code is the final arbiter of truth

This skill derives the ontology and auto-updatable docs **from the code**. When
code and a doc/ontology entry disagree, **the code wins** — update the doc to
match the code, never the reverse. Read source first (Step 2 orders code → docs →
high-level docs precisely so code is resolved before anything derived from it).
Recommend-only docs (architecture/diagrams) are flagged for human review rather
than auto-rewritten, but the conflict is still reported with code as reference.

## Workflow

### 1. Read checksums, identify dirty files

Read the checksums file; list all files where `last_tracked != last_resolved`. If
none, report "up to date" and stop. If `scope` is given, filter to code / docs /
a repo subtree.

### 2. Process dirty files in order: code → docs → high-level docs

1. **Source code** — read each file; extract entities, services, APIs, patterns,
   data models.
2. **Auto-updatable docs** (READMEs, agent-guidance files, inline docs) — check
   for drift from code, update if needed.
3. **Recommend-only docs** (architecture docs, diagrams) — read for intent; note
   recommendations but do NOT modify.

For each file, determine which overlay file(s) it affects (domain entities →
domain overlay; services/APIs/infra → services overlay; conventions/tooling →
conventions overlay; repo internals → per-repo overlay) and update them.

### 3. Cross-reference and consistency

After processing: check for orphaned entities (referenced but undefined), stale
references (defined but the source no longer contains them), and cross-repo
integration consistency between services overlay and per-repo files.

### 4. Update checksums

For each processed file set `last_resolved = last_tracked` and `resolved_at = now`.
Also update checksums for any overlay files modified this pass.

### 5. Report

Files processed; overlay files updated (entities/services/conventions/repo
changes); docs auto-updated; recommend-only changes (needs human review);
consistency issues found.

### 6. Commit ontology changes

Stage and commit all overlay changes + auto-updated docs under the
standards/quality role's commit identity.

## Docs update policy

| Doc type | Action |
|---|---|
| READMEs / agent-guidance / inline code docs | Auto-update to match code |
| High-level / architecture docs / diagrams | Read-only — recommend changes |

## What remains manual

- Recommend-only doc updates need human review.
- Structural ontology changes (new top-level categories) discussed first.
- Removing entities requires confirmation — prefer marking deprecated.
- **The structural index is never resolved here** — regenerate it via its
  generator (the lifecycle skills do this automatically at session-start and
  iteration wrap-up).

## Adaptation Notes

- The **code-is-arbiter** rule is the most transferable idea: docs/ontology are
  downstream artifacts brought into agreement with code, never the reverse.
- Keep the **resolver/generator separation** strict — hand-resolving a generated
  index defeats its always-current-by-regeneration property.
- Dirty-tracking via a checksums file makes the resolver incremental — only touch
  what changed.
